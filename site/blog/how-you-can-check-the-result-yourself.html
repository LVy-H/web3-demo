Verification · how-to

How you can check the result yourself

The whole point of Tessera is that you don’t have to take the organiser’s word for the result. So how do you actually check it? Here’s the verifier’s job, step by step—and an honest account of what each step proves.

In Tessera, the verifier is a first-class actor, not an afterthought. A verifier is anyone—a voter, the organiser, or a complete outsider—who wants to confirm the published result matches the ballots, without trusting the host or any service the Tessera authors run. The verification reads two public things: the published ballots from the server, and the anchored roots from the host-independent anchor. It trusts neither blindly; it cross-checks them.

Here are the six checks, in the order they run.

0. Registration closed before voting opened

This isn’t a check you run so much as a property you rely on: registration closes before voting begins. That fixes the set of issued credentials before any ballot is cast, which is what makes the later stuffing audit meaningful, and it breaks the timing link between “who registered” and “who cast.”

1. The setup can’t have shifted

You recompute the setupCommitment—a hash over the question, options, decision rule, ballot mode, roster commitment, the signing key, and the schedule—from the published metadata, and compare it to the value that was anchored before registration. If they match, the host did not quietly change the question or swap the credential key after the fact.

2. Every ballot carries a valid credential

Each ballot in the published set carries a credential whose blind signature verifies against the anchored per-decision public key, and that credential is bound to this decision (so it can’t be replayed from another vote). You also check that the number of issued credentials is no greater than the roster size.

Honest caveat: “issued ≤ roster” is necessary, not sufficient. The host defines the roster, so this check is a detection aid against over-issuance—not a proof against a host determined to stuff. Open, passcode, and domain rosters are published or member-challengeable so a member can dispute the count; that’s the real defence, and it rests on members watching.

3. No double-votes

You confirm there are no duplicate credential serials in the published set. That catches a voter trying to vote twice. (Host over-issuance is the roster limit from check 2, not this one—we’re careful not to conflate them.)

4. The tally and the verdict are honest

You recompute the result from the published ballots using the same open counting rule the server used—and crucially, you recompute the verdict, not just the raw count. “Carried,” “failed,” “tie,” “quorum-not-met”: the decision rule (threshold, quorum, tie-break) is part of what you re-derive and compare against the published result. A correct count under the wrong rule is still a wrong result, and the verifier catches that.

5. Nothing was dropped after it was acknowledged

This is the binding step that gives receipts their teeth. The final root is anchored; receipts are a signed hash-chain over the running log. You recompute the Merkle root over the served ballots and assert it equals the anchored root. Each receipt then yields an inclusion proof under that root. A valid receipt that does not resolve under the anchored root is exhibitable evidence of host misconduct—the kind of thing a single voter can hold up.

6. The challenge window

Between “closed” and “published,” there’s a window where receipt-holders submit receipts for inclusion proofs and roster members raise count challenges. A valid fraud proof flags the decision as disputed—anchored, so the dispute itself is on the record—even when there’s no central authority to adjudicate a self-hosted instance.

What this does — and doesn’t — prove

All six checks hold without any zero-knowledge proofs. That’s the design’s whole bet: the classical bulletin-board machinery is enough for the chosen threat model. But staying honest means being clear about the edges:

  • Checks 4 and 5 hold even against a malicious host—the tally is recomputable and tampering-after-acknowledgement is detectable.
  • Checks 2 and 3 are strong against voters but reduce to detection aids against a host that controls the roster. That limit is named, not hidden.
  • And every result carries a trust level so a receipt can never be mistaken for a stronger guarantee than it actually carries: anchored (chain), broadcast (signed root distributed), or casual (host-attested only, branded as trust-the-host).

That’s the honest version of “check it yourself”: a tally and verdict anyone can recompute, a history anyone can confirm wasn’t altered after the fact, and a clear label on exactly how much each result’s integrity rests on the host. For the full picture of where the line sits, read what Tessera does and doesn’t guarantee.
