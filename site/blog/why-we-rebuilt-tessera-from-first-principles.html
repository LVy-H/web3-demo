Design · first principles

Why we rebuilt Tessera from first principles

The old system rested on four big commitments. We re-opened every one of them and kept each only if the requirements earned it. Three didn’t survive intact.

The first version of Tessera was built feature-first, and its design was reverse-engineered into documents afterwards. That ordering quietly bakes in assumptions: a foundation gets chosen early, everything is built on top of it, and no one goes back to ask whether the foundation was ever the right one.

So we did the inverse. We wrote one coherent design from the top—requirements, then threat model, then architecture—and re-opened the four hard commitments the old system rested on: a blockchain backend, Semaphore zero-knowledge proofs, a gas-paying relayer, and one Flutter client. Each one had to re-earn its place against the actual requirements. Three of the four did not survive intact.

The headline: it’s a trust problem, not a scale problem

Tessera is not a scale problem, it is a trust problem.

Once you admit that, a lot of heavy machinery turns out to be solving a problem this product doesn’t have. The decisions Tessera is for—a club, a board, a co-op, a working group—involve tens to a few thousand voters. Every ballot ever cast fits in megabytes. Peak load is a fraction of a vote per second. Throughput, sharding, caching, storage tiers: all non-issues.

All the real pressure is on three things—integrity, privacy, and trust—and none of those is a scale axis. A smart-contract chain, Groth16 proving, and a gas-paying relayer are powerful tools, but they were answering a scaling and trustlessness question we weren’t actually being asked.

The threat model that did the cutting

What are we being asked? We settled the threat model first, in one line:

Trust the organiser for integrity, but prove the count to everyone.

That is the honest situation for most groups. You generally do trust whoever set up the vote not to be running an active attack—but everyone else still wants to check the result, not just be told it. That’s a far weaker requirement than “assume the organiser is malicious,” and the weaker requirement is what let us delete most of the stack.

The verdict on the four foundations

  • Blockchain backend → demoted to a notary, and not even the default. A chain was only ever needed for one narrow thing: host-independent non-equivocation of the checkpoint roots—and only when a host is willing to fund a wallet. The default anchor is now a zero-wallet signed-root broadcast that’s tamper-evident if any voter keeps it. The chain becomes an optional equivocation-resistance upgrade. That drops roughly two thousand lines of Solidity.
  • Semaphore / Groth16 zero-knowledge → dropped from 1.0, parked as “strong mode.” A blind-signature credential meets the chosen threat model with no circuit and no prover. ZK’s real residual value—permissionless membership and anonymity that doesn’t rest on the host—maps exactly onto a future “strong mode.” So we parked the proven code as an option rather than deleting it.
  • Relayer → dropped. It existed for one reason: to pay gas for on-chain votes. With no on-chain votes, ballots just POST to the server. The relayer’s job vanished with the chain.
  • One Flutter client → kept, but gated on a hard web-payload budget. Reusing the design system and product code is worth a lot, but the voter path has to load fast on a throttled phone. So the voter-path payload is a CI gate, with a thin web voter shell as a pre-planned fallback—not an emergency—if Flutter web can’t hit the budget.

Where it landed: a verifiable bulletin board

Two requirements collide and force the whole design: self-host it yourself, and verify the result without trusting the host. If the host controls the server, the record can’t live only on that server—we need one thing the host can’t forge.

That is the classic verifiable bulletin-board pattern, from the Helios/Belenios lineage, with a self-host twist: the board lives on the host’s own server, but its checkpoints are pinned to a public, host-independent anchor. The pieces are deliberately classical—an append-only ballot log, blind-signature credentials for anonymous-yet-eligible ballots, and an anchored commitment—and they satisfy the requirements provided we are honest about exactly which trust they do and don’t remove.

Honesty as the load-bearing part

That last clause is the whole game. A first design draft is easy to oversell. So we ran it through a four-lens adversarial review—security, systems, product, red-team—and the most important output wasn’t new features. It was making the honesty load-bearing rather than aspirational: naming, in the spec itself, that secret-ballot privacy doesn’t hold against a live malicious host, that a host who controls the roster can stuff up to its roster-control budget, and that censorship-by-silence is detectable only as deletion-after-acknowledgement.

Those aren’t footnotes we hide—they’re on the honesty page, in the product’s trust-level labels, and in the design doc’s threat model. The differentiator that survives is genuine but narrow: anonymous-yet-eligible ballots with a publicly recomputable tally and a tamper-evident history—not “trustless.”

This post summarises the system design (sections 0 and 8) and the roadmap’s “what changed and why.” The full design doc, including the adversarial-review log, lives in the repository. The dismantle-and-rebuild work is in progress—the design and server foundations are landing first; the trust core (credentials, checkpoints, anchor, verifier) and the client rewire follow.
