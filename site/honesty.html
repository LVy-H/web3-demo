The credibility anchor

What Tessera does — and doesn’t — guarantee.

Most voting tools market the strong-sounding version and stay quiet on the limits. We do the opposite. This page is the honest threat model, stated as plainly as we can: where “you can check it” has real teeth, and where it reduces to trusting the host.

Tessera’s threat model is “trust the organiser for integrity, but prove the count to everyone.” The convener/host is trusted for integrity but checked. The honest work below is being precise about where that check is a mechanism the host can’t cheat, and where it’s a detection aid that ultimately rests on host honesty.

Holdseven against a malicious host

Mechanism, not policy.

These properties hold because of how the system is built—not because we ask the host to behave. A dishonest host cannot break them without producing evidence anyone can exhibit.

Guaranteed by mechanism

  • Tally correctness. Anyone can recompute the result and the verdict (carried / failed / quorum-not-met) from the published ballots, using the same open counting rule. If the published result doesn’t match what the ballots produce, the discrepancy is visible to everyone.
  • Ballot-set tamper-evidence after acknowledgement. Receipts are a signed hash-chain over the running log, and the log’s roots are anchored (interim and final). Dropping, reordering, or altering an acknowledged ballot breaks a chain that a receipt-holder can exhibit. A verifier must recompute the Merkle root from the served ballots and assert it equals the anchored root—that binding step is what gives the receipt its force.
  • Setup immutability. The question, options, decision rule, roster commitment, and the per-decision signing key are committed in a setupCommitment and anchored before registration opens. The host can’t quietly change the question or swap the credential key after the fact.

Restson host honesty — named limits

Where the check becomes a detection aid, not a proof.

These are real limits. We do not overclaim them. Tessera includes detection aids that make abuse harder and more visible—but a determined, dishonest host can still operate inside these gaps. If your group cannot trust the organiser this far, 1.0 is the wrong tool (see the post-1.0 “strong mode” below).

Named limits — do not overclaim

  • Eligibility & ballot-stuffing. The host defines the roster, so it can stuff via fake-eligible identities or by casting the credentials of no-shows. In secret mode, blind signatures make stuffed ballots indistinguishable from real ones. Mitigations: open / passcode / domain rosters are published or member-challengeable (a member can publicly dispute “you say 47 registered but only 30 of us did”); secret mode publishes per-identity issuance counts for member audit. Residual: a determined host can stuff up to its roster-control budget. The “no double-vote” and “issued ≤ roster” checks are detection aids, not proofs against the host on eligibility.
  • Secret-ballot privacy against a live malicious host. One self-hosted process does eligibility, blind-signing, and the ballot box, so it could correlate register ↔ cast by timing, IP, or session. Blind signatures hide the token, not the act. Mitigations: registration closes before voting opens (breaks the issuance ↔ cast ordering), casts use a fresh session, turnout is coarse. Residual: a host that logs metadata can narrow the anonymity set—badly in small groups. Secret mode protects against participants, outside observers, and after-the-fact forensics—not a live malicious host.
  • Censorship by silence. A host can drop a ballot and simply return no receipt; the voter then has nothing to exhibit. Receipts prove deletion-after-acknowledgement, not refusal-to-acknowledge. (Partial mitigation: a server-signed acknowledgement of submission before commit gives the voter something to hold.)

Every result carries its trust level. anchored (chain, equivocation-resistant) · broadcast (signed root distributed, tamper-evident if kept) · casual (host-attested only, branded “trust-the-host”). A receipt can never be mistaken for a stronger guarantee than it actually carries.

Out of scopeby the core job

What Tessera deliberately does not try to do.

Not in scope (1.0)

  • Coercion-resistance / vote-buying. Receipt-freeness (the MACI class of problems) is a different product with much heavier machinery. Tessera’s self-contained receipts are explicitly not coercion-resistant.
  • Anonymity against global blockchain validators. No ballots ever go on-chain—the chain, when used, is a notary for checkpoint roots only.
  • Nation-state availability. Tessera is sized for clubs, boards, co-ops, and working groups—tens to thousands of voters per decision—not for resisting a state-level adversary.

The upgrade path — named, not vague

If you need privacy against the host itself.

The honest limits above are not permanent. The two host-trust gaps—stuffing and live-host privacy—have a named fix on the roadmap: a “strong mode” that splits trust so no single party can break secrecy or stuff the roster.

  • ▸Separate registrar ⊥ ballot box (Belenios-style). Recovers an “either-party-honest” guarantee—privacy holds unless both parties collude.
  • ▸Parked Semaphore zero-knowledge credential. For permissionless, host-independent membership anonymity. The proven code is parked, not deleted—kept as an option, not a promise.
  • ▸Witnessed-log anchor. No-wallet non-equivocation—stronger than broadcast mode without needing a funded wallet.

These are post-1.0: an upgrade path, not something 1.0 silently claims. We’d rather name the limit and the fix than blur the line.
