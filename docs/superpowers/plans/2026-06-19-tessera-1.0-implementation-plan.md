# Tessera 1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate Tessera from the on-chain + ZK + relayer stack to a self-hosted verifiable
bulletin board (server + blind-signature credentials + commitment anchor), reaching a
shippable 1.0 with honest, review-hardened trust guarantees.

**Architecture:** A single self-hostable **server** holds an append-only ballot log; secret
ballots use **blind-signature credentials**; the log's checkpoints are pinned to a
**public anchor** (signed-root broadcast by default, an L2 chain as the upgrade). The
existing **Flutter client + design system + journey state machines + off-chain tally** are
kept and rewired to the server. Canonical design:
[`../specs/2026-06-19-tessera-system-design.md`](../specs/2026-06-19-tessera-system-design.md).

**Tech Stack:** Flutter/Dart (client, melos workspace at `codes/app/`); TypeScript +
Express + Vitest (new server, seeded from the retired relayer scaffolding); SQLite (WAL);
RSABSSA-PSS blind signatures (RFC 9474); RFC 6962-style Merkle log; an L2 chain SDK for the
optional anchor.

## Global Constraints

- **Threat model is "trust the organiser for integrity, prove the count to everyone."** No
  task may claim a guarantee the design doc §6 marks as host-trusted (eligibility/stuffing,
  secret-ballot privacy vs a *live* host, censorship-by-silence). "Strong mode" (registrar
  separation / ZK) is **post-1.0** — do not build it in 1.0 unless the owner re-scopes.
- **No ZK, no on-chain voting, no relayer in 1.0.** The chain is a commitment notary only.
- **Self-host default needs no crypto wallet** — broadcast anchor mode is the default; the
  chain anchor is opt-in.
- **Keep, don't rewrite:** `design_system`, `core_domain` (journeys + `voting/` tally),
  `core_storage`, the `feature_*` UI screens + ballot widgets, `join_grammar`. Reuse the
  `core_relay` HTTP-client shape and the relayer's Express/Vitest scaffolding.
- **Verifier recomputes the verdict, not just the tally** (quorum/threshold/tie).
- Voter web path: WCAG 2.1 AA + a hard payload budget (≤~1 MB, ≤~3 s cold load on throttled
  4G), CI-gated; thin web shell is the pre-planned fallback.
- Commits: existing git identity (`Hoang <hoangstlt@gmail.com>`); **no AI-signature
  trailers/footers.** Conventional-commit style, matching the repo.

## Phases 2–6 — task maps  *(each gets its own detailed plan at execution time)*

> These depend on Phase 1's seam and on design decisions that should be re-confirmed when
> reached (plan-before-implement). Decomposed to task granularity here; expanded to
> bite-sized TDD steps in a per-phase plan under `docs/superpowers/plans/` when started.

### Phase 2 — The server (open-ballot end-to-end)
- **2.1 Storage layer** — SQLite (WAL, busy_timeout, single-writer); migrations; the
  `Decision`, `Ballot`, `Receipt`, `Checkpoint`, `Account`, `LifecycleEvent`,
  `EligibilityRecord`, `IssuedCredential` tables (design §9). *Deliverable:* typed repo with
  append-only invariant tests.
- **2.2 Convener auth** — bootstrap admin token (printed on first run) + per-convener bearer
  tokens; middleware gating convener routes. *Deliverable:* authed lifecycle routes.
- **2.3 Decision lifecycle** — `POST /decisions`, `/open|/close|/publish|/extend|/cancel`,
  state machine + signed `LifecycleEvent`s; `setupCommitment` computation (design §9 preimage).
- **2.4 Eligibility** — open/invite/passcode/domain methods + abuse controls (rate-limit,
  maxParticipants); SMTP pluggable for domain/reminders.
- **2.5 Cast (open ballot) + receipts** — `POST /ballots` with idempotencyKey, single-txn
  ballot+receipt commit, the shared tally oracle ported from `core_domain/voting/`.
- **2.6 Public read API** — `GET /decisions/:id`, `/ballots` (cursor-paginated), `/root`,
  `/results`, `/anchor`; signed error model.
- **Exit:** open-ballot decision create→open→cast→close→publish e2e + a self-contained receipt;
  one-command broadcast-mode deploy.

### Phase 3 — Trust core (secret ballots + verifiable)
- **3.1 Blind-sign issuer** — per-decision RSABSSA-PSS keypair; `POST /register` issues a
  blind-signed credential; pubkey hash in `setupCommitment`; registration-closes-before-voting.
- **3.2 Merkle log + running checkpoints** — RFC 6962 domain-separated hashing; receipts sign
  the running root; interim + final checkpoints.
- **3.3 Anchor adapter** — `broadcast` (default; distribute signed final root), `chain` (L2 tx
  with status/finality/reorg handling, `closed-pending-anchor`), `casual`; trust-level (V5).
- **3.4 Public verifier** — recompute tally **+ verdict**; recompute Merkle root == anchored
  root (binding step); serials + inclusion; challenge window.
- **Exit:** an independent verifier validates a secret-ballot decision against the anchor
  without trusting the server; verification protocol (§11) holds.

### Phase 4 — Client rewire + web-payload gate
- **4.1 Server port adapters** — implement the kept `VoterJourneyPort`/`BlindJourneyPort`/
  `OrganizerJourneyPort` against the server API (replace `UnimplementedJourneyPort`); repoint
  `core_relay/relay_client.dart` + `core_chain/chain_reader.dart` to server endpoints.
- **4.2 Self-contained receipts + V5 trust-level UI + returning-voter/shared-device (P7).**
- **4.3 Web-payload spike → CI gate** on the voter path; thin web shell fallback if Flutter web
  misses the budget (design §12.4).
- **Exit:** full voter/convener/verifier flows in-client against the server; payload budget is
  a green CI gate (or shell fallback in place).

### Phase 5 — Product completeness (review-surfaced FRs)
- **5.1 Result semantics** — quorum/threshold/tie-break config → published verdict; verifier
  recomputes it.
- **5.2 Notifications/reminders** (opt-in channel). **5.3 Lifecycle edit/cancel/extend.**
  **5.4 Abstain/none-of-the-above.** **5.5 Result share/export** (link/QR, CSV, PDF).
- **5.6 Accessibility** to WCAG 2.1 AA on the voter path; externalise strings (i18n-ready).
- **Exit:** a real club/student-org/board runs a decision end-to-end and returns to it, accessibly.

### Phase 6 — 1.0 hardening & release
- **6.1 Security review** of the verification protocol + credential/key handling; durability/
  crash tests; abuse hardening. **6.2 One-command self-host packaging + ops docs** (TLS,
  `data/` backup incl. keys, the optional funded-wallet anchor). **6.3 Truth-up + cut 1.0.**
- **Exit (1.0 bar):** verification holds; voter path WCAG-AA + within budget; one-command
  self-host (broadcast default); honest claims (§13) match reality.
